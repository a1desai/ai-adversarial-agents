## 1. Executive Summary

The Adversarial Cybersecurity Sandbox is a zero-budget, fully open-source Attack & Defense (A&D) system in which two
autonomous multi-agent pipelines operate concurrently against Dockerized web-application targets:

- **Red Team** — discovers, chains, and exploits vulnerabilities without human guidance.
- **Blue Team** — monitors logs, reverse-engineers the active exploitation path, and generates + validates a
  code-level patch that neutralizes the vulnerability without breaking application functionality.

Both pipelines run on distributed student hardware (≤6 GB VRAM, 7–8B local models via Ollama), under strict
step/token/wall-clock caps, with **no paid APIs, no cloud, and no licensed software**. The headline research
questions this report answers are:

1. Does the autonomous exploitation pipeline work end to end, and at what **Exploit Success Rate (ESR)**?
2. Does the autonomous defense pipeline work end to end, and at what **Patch Success Rate (PSR)**?
3. How do results compare to the calibrated baselines, and where should effort go next?

The qualitative findings (methodology, architecture, reward design, what worked / what didn't, next steps) are
final and evidence-backed. A **single-target smoke run** (n = 1, DVWA / CVE-2019-9053) has been executed and its
real numbers appear in §3–§4; the **suite-level** quantitative findings (the 40-CVE CVE-Bench run) are still
**pending** and marked `TBD`.

## 6. Methodology

Adapted from Red Team Report §6 and Blue Team Report §6 (Validation and Correctness Testing).

### 6.1 Gold-standard benchmark
The primary validation instrument is **CVE-Bench v2.1.0**: 40 critical-severity CVEs with fully containerized
environments, automated grading servers, and human-verified reference exploits. A Red target is marked exploited
**only if the CVE-Bench grader confirms** at least one of the eight standard attack goals (denial of service,
unauthorized login, privilege escalation, database access, database modification, file access, file creation,
remote code execution).

### 6.2 Red validation — multi-stage
1. **Automated grading** — the CVE-Bench server checks for standard attack outcomes programmatically.
2. **Trace replay** — every successful exploit chain is replayed against a clean container; a replay failure
   invalidates the original success (see the validity gate, §6.5 below).
3. **Human audit (20% sample)** — random sample reviewed by a team member with pentest experience.
4. **False-positive detection** — the Verification Agent independently re-checks the grader endpoint.

### 6.3 Blue validation — dual (functional + security)
Unlike the Red Team, the Blue Team must pass **two** independent checks: the patch must **block the exploit**
(security) **and** the application must **keep working** (functional). A patch that blocks an exploit by crashing
the app is not a success. The staged protocol is: patch-application test → functional test → security test
(exploit replay) → regression scan → 20% human audit.

### 6.4 Determinism and reproducibility
Every engagement gets a unique `trace_id`; every action (tool call, LLM prompt/response, state transition) is
recorded with timestamps by `evaluation/trace_logger.py` into `evaluation/traces/{trace_id}.jsonl` plus a
`{trace_id}_summary.json`. Successful engagements must be reproducible by replaying the logged actions against a
fresh container instance.

### 6.5 Trace-replay validity gate (#74)
Before any success counts toward ESR/PSR, its trace is **replayed** against a clean target. **A success that does
not reproduce on replay is dropped from the numerators.** This gate (#74) is what keeps the headline metrics
honest — it converts "the model claimed success" into "the success reproduces deterministically." The benchmark
run therefore reports *replay-validated* ESR/PSR, not raw claim rates.

### 6.6 Metric definitions
- `ESR = successful_exploits / total_targets`
- `PSR = successful_patches / total_targets`
- Composite rewards per §7 below, computed entirely outside the LLM.

## 7. Reward Design Rationale

Adapted from Red Team Report §5 and Blue Team Report §5. The reward function is **not** a training signal (the
agents use pre-trained LLMs, not RL); it exists to (a) measure whether the architecture improves across iterations
and (b) feed the Supervisor's continue/retry/terminate routing.

### 7.1 Red composite reward
Implemented in `evaluation/reward_red.py`:

```
R_red = 0.40·ESR + 0.20·TTE + 0.10·diversity + 0.15·efficiency + 0.10·adaptation − 0.05·grounding_penalty
```

| Component | Weight | Externally verified from |
| --- | --- | --- |
| Exploit Success Rate | 0.40 | CVE-Bench grader endpoint |
| Time-to-Exploit | 0.20 | wrapper wall-clock timer |
| Attack diversity | 0.10 | unique attack types / 8 |
| Efficiency | 0.15 | wrapper token ledger |
| Adaptation | 0.10 | Supervisor retry tracker (attempt N vs N+1) |
| Grounding penalty | −0.05 | wrapper evidence checker vs actual tool output |

### 7.2 Blue composite reward
Implemented in `evaluation/reward_blue.py`:

```
R_blue = 0.35·PSR + 0.15·minimality + 0.15·TTP + 0.15·functional_preservation + 0.10·efficiency − 0.10·grounding_penalty
```

| Component | Weight | Externally verified from |
| --- | --- | --- |
| Patch Success Rate | 0.35 | exploit replay against patched container |
| Patch minimality | 0.15 | diffstat on the actual patch |
| Time-to-Patch | 0.15 | wrapper wall-clock timer |
| Functional preservation | 0.15 | functional tests against patched container |
| Efficiency | 0.10 | wrapper token ledger |
| Grounding penalty | −0.10 | source-code analyzer vs Vulnerability Analysis scope |

### 7.3 Two design principles that make the rewards trustworthy
- **Anti-exploitation:** the reward function is computed **entirely outside the LLM's awareness** — the model never
  sees the composite score or the weights, and is never prompted to optimize any metric. If future iterations add
  online reward shaping, the weights must be treated as privileged and never enter any prompt.
- **Grounding over "don't hallucinate":** you cannot instruct an LLM not to hallucinate; hallucination is intrinsic.
  Instead the wrapper measures something observable and enforceable — whether an action (Red) or a code change
  (Blue) is supported by actual tool output / the Vulnerability Analysis. This is computed externally and cannot be
  gamed by the model.

Within an engagement, lightweight micro-rewards guide routing (e.g., Red: +10 for a grader-confirmed exploit,
−2 for a repeated identical action; Blue: +10 for blocking the exploit, −5 for breaking the app).

## 8. Architecture Summary

Both teams share the same shape: a **LangGraph** state machine over a typed state, orchestrated by a **Supervisor**
node, with agents talking to targets over an **MCP** transport layer, backed by episodic/procedural/semantic memory
in **ChromaDB**. Everything runs locally via **Ollama** on ≤6 GB VRAM.

### 8.1 Red Team pipeline (`agents/red_team/`)
`create_red_team_graph()` builds a LangGraph over `RedTeamState`. Phases (`AttackPhase`):
`init → recon → exploitation → verification → complete/failed`. Agents: **ReconAgent** (attack-surface map),
**ExploitationAgent** (`plan_attack`, `execute_payload`), **VerificationAgent** (`verify`, independent grader
re-check). Hard caps: **MAX_STEPS=30, MAX_TOKENS=50000, MAX_RETRIES=3** (plus a 15-minute wall-clock cap).
Outcome ∈ `success/failure/partial/timeout`.

### 8.2 Blue Team pipeline (`agents/blue_team/`)
`create_blue_team_graph()` builds a LangGraph over `BlueTeamState`. Agents: **LogAnalysisAgent** →
**RootCauseAgent** → **PatchGenerationAgent** → **PatchValidationAgent**. The Blue Team is **event-driven**: it
activates only on a confirmed exploit, not on a timer. Its context demands are higher than Red's (attack evidence +
source + CVE data + patch memory held simultaneously), so MCP truncation and targeted source extraction are
critical.

### 8.3 Shared infrastructure
- **Trace logging:** `evaluation/trace_logger.py` → `evaluation/traces/`.
- **Rewards:** `evaluation/reward_red.py`, `evaluation/reward_blue.py`.
- **Benchmark harness:** `benchmark_runner.py` (#16/#41, PR #66) → `evaluation/results/{benchmark_results,summary,checkpoint}.json`.
- **Reporting:** `evaluation/report_generator.py` (#72) reads those results and fills this document's tables.
- **Isolation:** air-gapped Docker network, `--cap-drop=ALL`, read-only rootfs, host firewall.

## 9. What Worked

*(Qualitative, from delivered artifacts and the reports; no run data required.)*

- **End-to-end pipelines exist and are testable fully mocked.** Both graphs are constructed, typed, and exercised
  by unit/integration tests with Ollama + ChromaDB mocked — the "working framework first" goal (§1 of both reports)
  is met at the code level.
- **Externally-computed, un-gameable rewards.** Rewards are implemented outside the LLM and derived from grader,
  timer, token ledger, diffstat, and source analysis — not model self-report (§5 of both reports).
- **Grounding penalty instead of an un-enforceable "don't hallucinate."** A concrete, measurable signal replaces a
  wish, and it can't be gamed by the model.
- **Deterministic trace logging with replay.** Every engagement is reproducible via `trace_logger` + the #74
  replay gate, which is what lets ESR/PSR be reported as *validated* rather than *claimed*.
- **Hard safety and termination caps.** Steps/tokens/wall-clock caps + episodic-memory repeat detection directly
  neutralize the highest-likelihood technical risks (infinite loops, context saturation).
- **Zero-budget constraint held.** Local 7–8B models on ≤6 GB VRAM, all open-source — no paid dependency crept in.

## 10. What Didn't Work / Open Risks

*(From the risk registers — Red §11 and Blue §11 — plus current repo state.)*

- **No live benchmark numbers yet.** The single biggest gap: `benchmark_runner` is unmerged (PR #66), so ESR/PSR/
  reward are all `TBD`. This report's quantitative half cannot close until the #16/#41 pipeline runs.
- **Small-model hallucination (High).** 7–8B models fabricate exploit chains / patches more than frontier models.
  Mitigated by Verification/Patch-Validation agents, grounding penalty, and replay — but expected to be the top
  failure bucket once §5 is populated.
- **Low absolute success rate expected (High).** Calibrated targets are deliberately modest (Red 3–5%, Blue 5–10%)
  and below frontier baselines (13% / 21–23%). Falling in-range is success for a working framework, not SOTA.
- **Context-window saturation (High).** Effective context degrades well before the nominal max at 7–8B; Blue is more
  exposed than Red. Mitigated by aggressive MCP truncation (<1,000 tokens/tool output) and targeted extraction.
- **Regression introduction (Blue, High).** Patches can block the exploit but break the app; mandatory functional
  tests + the functional-preservation metric guard against this, but it remains a leading Blue failure mode.
- **Insufficient attack evidence (Blue, Medium).** If Red leaves thin log traces, Blue may lack signal to
  reconstruct the attack; packet-capture supplement + grader-goal query partially mitigate.
- **Red–Blue synchronization (Medium).** Timing coupling between exploit and response; mitigated by event-driven
  Blue activation on confirmed exploit only.
- **Operational:** heterogeneous student hardware (High, target 6 GB VRAM floor) and container-escape (Low
  likelihood / Critical impact, mitigated by air-gapped isolation).

## 11. Recommended Next Steps

1. **Merge the benchmark harness and run it.** Land PR #66 (#16/#41 pipeline), execute a full CVE-Bench pass, then
   run `report_generator.py` (#72) to replace every `TBD` in §2–§5 with replay-validated numbers.
2. **Gate all reported successes behind trace replay (#74).** Make the #74 validity gate a hard precondition in the
   runner so raw claim rates can never leak into ESR/PSR.
3. **Attack the top failure bucket first.** Once §5 is populated, invest where the counts are — most likely
   hallucination/grounding (Red) and regression/patch-location (Blue).
4. **Grow procedural memory with validated playbooks/patch templates.** The reports' primary lever for raising
   ESR/PSR beyond baseline is a richer, validated procedural memory, not bigger models.
5. **Prompt refinement + retrieval tuning.** Iterate recon/exploitation and root-cause/patch prompts; tune ChromaDB
   retrieval budgets to fight context saturation.
6. **Start on simpler vulnerability classes.** Concentrate early Red effort on lower-complexity CVEs to establish a
   non-zero, reproducible ESR before scaling to multi-step chains.
7. **Use supplementary corpora as diagnostics.** CTF challenges (Red) and known NVD patch pairs (Blue) widen the
   evaluation surface independent of CVE-Bench and of Red's success rate.
8. **Track reward trend across iterations.** Log composite rewards per run and compare across architecture changes —
   the reward exists precisely to measure iteration-over-iteration improvement.
